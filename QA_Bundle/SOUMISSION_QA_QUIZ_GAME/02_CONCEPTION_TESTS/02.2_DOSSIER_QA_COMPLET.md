## 1. INFORMATIONS PROJET & OBJECTIFS

### 1.1 Vue d'ensemble
Quiz Game est une application web full-stack permettant aux utilisateurs de participer à des quiz interactifs dans quatre catégories (Computer Science, Mathematics, General Knowledge, Sports). Les fonctionnalités clés incluent l'inscription, la connexion, la participation à un quiz complet, la sauvegarde du meilleur score par catégorie et la consultation d'un leaderboard global.

### 1.2 Objectifs métier
- Plateforme d'évaluation interactive et engageante.
- Suivi personnalisé des performances par utilisateur et par catégorie.
- Motivation par la compétition via un classement dynamique.
- Expérience fluide et responsive sur navigateurs modernes.

### 1.3 Parties prenantes
- **Utilisateurs finaux** : joueurs souhaitant tester leurs connaissances.
- **Administrateurs système** : gestion des questions et de la base MongoDB.
- **Équipe de développement** : maintenance et évolutions.
- **Product Owner** : priorisation fonctionnelle et validation.

## 2. ARCHITECTURE, DONNÉES & API

### 2.1 Stack technologique
**Frontend** : Angular 18.2 (TypeScript, Standalone Components, Angular Signals, Angular Router, HttpClient, LocalStorage).  
**Backend** : Node.js + Express 4.21, MongoDB via Mongoose 8.9, bcrypt 5.1.1, CORS, body-parser, dotenv.  
**Pattern** : MVC, communication REST, déploiement Angular (port 4200) / Express (port 5000).

### 2.2 Modèles de données
**User Schema**  
```javascript
{
  username: String (required, unique),
  email: String (required, unique),
  password: String (required, hashed),
  scores: [Number] // [CS, Maths, GK, Sports]
}
```

**Question Schema**  
```javascript
{
  question: String (required),
  incorrectAnswers: [String],
  correctAnswer: String (required),
  category: Enum ['Computer Science', 'Maths', 'General Knowledge', 'Sports']
}
```

**Exemples d'objets**  
_User_  
```json
{
  "_id": "507f1f77bcf86cd799439011",
  "username": "john_doe",
  "email": "john@example.com",
  "scores": [5, 8, 7, 6]
}
```

_Question_  
```json
{
  "_id": "507f1f77bcf86cd799439012",
  "question": "What is Angular?",
  "incorrectAnswers": ["A database", "A language", "An OS"],
  "correctAnswer": "A framework",
  "category": "Computer Science"
}
```

_Login Response_  
```json
{
  "message": "Login successful",
  "user": {
    "_id": "507f1f77bcf86cd799439011",
    "username": "john_doe",
    "email": "john@example.com",
    "scores": [5, 8, 7, 6]
  }
}
```

### 2.3 Endpoints API
**Authentification et utilisateurs**  
```
POST /api/users/register
POST /api/users/login
GET  /api/users
GET  /api/users/leaderboard
PATCH /api/users/score/:userId
GET  /api/users/test
```
**Questions**  
```
POST /api/questions
GET  /api/questions?category={category}
```

## 3. CATALOGUE COMPLET DES USER STORIES

### 3.1 Module Authentification — US-AUTH-001
**En tant qu'utilisateur** je veux m'inscrire, me connecter et me déconnecter pour sécuriser mon accès.  
**Critères d'acceptation** :
1. Création compte (email, username, password & confirmation) avec validation unicité.
2. Mot de passe hashé (bcrypt salt=10), scores initiaux [0,0,0,0], redirection vers /login.
3. Messages d'erreur explicites pour doublons.
4. Connexion via email + mot de passe, stockage localStorage (sans password), redirection /welcome.
5. Message "Invalid email or password" en cas d'échec, loader durant la requête.
6. Persistance session via localStorage.
7. Bouton Logout accessible sur /welcome, supprime les données et redirige vers /login.
8. AuthGuard protège /welcome, /quiz, /leaderboard (redirection /login si non authentifié).
9. Routes /login et /register publiques, mot de passe jamais renvoyé via API.
**Règles métier** : unicité email/username, pas de stockage en clair, session client via localStorage, nettoyage complet à la déconnexion.  
**Priorité** : MUST HAVE — 13 points.

### 3.2 Module Quiz — US-QUIZ-001
**En tant qu'utilisateur connecté** je veux sélectionner une catégorie, répondre et voir mes résultats.  
**Critères d'acceptation (sélection & démarrage)** :
1. Affichage 4 catégories avec cartes/icônes.
2. Sélection unique avec état visuel, bouton Start désactivé tant qu'aucune carte n'est choisie.
3. Catégorie sauvegardée dans localStorage, loader pendant la requête GET `/api/questions`.
4. Redirection vers /quiz, compteurs réinitialisés.
**Affichage & réponses** :
5. Question + 4 réponses mélangées, compteur "Question X/Y".
6. Mise en évidence de la bonne réponse (vert) et de la mauvaise (rouge), blocage des clics après sélection.
7. Bouton "Next question" apparaît après réponse, navigation linéaire sans retour.
**Résultats & sauvegarde** :
8. Écran "Congratulations", score "X out of Y right", bouton retour menu.
9. Sauvegarde automatique du score via PATCH `/api/users/score/:userId`, conservation du meilleur score.
**Gestion des erreurs** : messages console/UX si absence de questions ou échec sauvegarde.
**Règles métier** : mélange aléatoire, réponse unique, pas de modification après choix, score = nb réponses correctes, sauvegarde asynchrone, meilleur score uniquement.  
**Priorité** : MUST HAVE — 21 points.

### 3.3 Module Leaderboard — US-LEAD-001
**En tant qu'utilisateur connecté** je veux consulter le classement global/par catégorie.  
**Critères d'acceptation** :
1. Bouton Leaderboard (icône trophée) sur /welcome, route protégée, bouton Back to Menu.
2. Tableau colonnes Rank, Username, CS, Maths, GK, Sports, Total Score ; tri décroissant sur total, rang calculé.
3. Message "No users found" si base vide.
4. Chargement automatique via GET `/api/users/leaderboard`, retour uniquement username + scores, tri côté client, erreurs loggées.
**Règles métier** : tous les utilisateurs listés (même score 0), total = somme des 4 scores, pas de rafraîchissement temps réel, rechargement manuel.  
**Priorité** : MUST HAVE — 8 points.

### 3.4 Gestion Catégories & Scores — US-DATA-001
**En tant que système** je veux définir les catégories de quiz et les scores.  
**Critères d'acceptation** :
1. 4 catégories fixes (Computer Science, Maths, General Knowledge, Sports) définies en enum.
2. Mapping index (CS=0, Maths=1, GK=2, Sports=3) géré par `getCategoryIndex`, -1 pour valeurs invalides.
3. Validation obligatoire du champ category (création/modification) ; insertion invalide rejetée.
4. Initialisation scores à [0,0,0,0], tableau toujours de 4 éléments.
5. PATCH `/api/users/score/:userId` reçoit `{categoryIndex, score}` (0–3).
6. Erreurs 400 pour index hors plage, 404 si user absent.
7. Mise à jour seulement si score plus élevé (high score only), erreurs loggées sans bloquer.
8. `calculateTotalScore` = somme des 4 valeurs, résultat non stocké en base.
**Règles métier** : catégories non modifiables, correspondance stricte, pas de scores négatifs ni d'historique, modification atomique du tableau.  
**Priorité** : MUST HAVE — 13 points.

### 3.5 User Stories Non-Fonctionnelles
- **US-NFR-001 — Performance de chargement** : LCP & TTI < 3s, API p95 < 500 ms, bundles optimisés, assets compressés, lazy loading. (SHOULD HAVE, 5 pts)
- **US-NFR-002 — Sécurité des données** : bcrypt ≥ 10, mot de passe jamais retourné, HTTPS prod, CORS restreint, prévention injections, implémentation future JWT. (MUST HAVE, 8 pts)
- **US-NFR-003 — Compatibilité navigateurs** : Chrome/Firefox/Safari/Edge (2 dernières versions), design responsive. (SHOULD HAVE, 5 pts)
- **US-NFR-004 — Gestion des erreurs** : messages UX clairs, logs serveur, middleware global, réponses cohérentes 4xx/5xx, gestion erreurs réseau. (MUST HAVE, 8 pts)
- **US-NFR-005 — Accessibilité (A11y)** : navigation clavier complète, labels associés, contraste AA, aria-labels, parcours logique. (COULD HAVE, 8 pts)
- **US-NFR-006 — Scalabilité** : 10k utilisateurs, indexes optimisés, 100 requêtes simultanées, pagination, cache envisagé. (SHOULD HAVE, 13 pts)
- **US-NFR-007 — Maintenabilité** : respect MVC, composants standalone, DI, conventions TS/JS, config externalisée, commentaires pour logique complexe. (SHOULD HAVE, effort continu)

## 5. PÉRIMÈTRE & STRATÉGIE DE TEST

### 5.1 Éléments à tester
| Élément | Description | Objectif |
|---------|-------------|----------|
| Front-end Angular | Composants Login, Register, Welcome1, Quiz, Leaderboard, AuthGuard, services auth & quiz. | Vérifier UX des user stories, responsive design. |

| Base MongoDB | Schémas User/Question, validations enum, opérations scores. | Intégrité données, initialisation scores, meilleur score. |
| Flux Auth complet | Inscription → Connexion → Navigation protégée → Déconnexion + localStorage. | Routes protégées et nettoyage session. |
| Calculs Score/Classement | `calculateTotalScore`, tri leaderboard, règle high score only. | Alignement UI ↔ base, cohérence tri. |

### 5.2 Caractéristiques à tester
1. Authentification unifiée (US-AUTH-001).
2. Parcours Quiz complet (US-QUIZ-001).
3. Leaderboard dynamique (US-LEAD-001).
4. Gestion Catégories & Scores (US-DATA-001).
5. Exigences NFR prioritaires (Performance, Sécurité, Gestion erreurs).

### 5.3 Caractéristiques hors scope
1. Fonctionnalités sociales (badges, partage, commentaires).
2. Mode multijoueur temps réel.
3. Création/édition de quiz personnalisés.
4. Accessibilité AAA.
5. Applications mobiles natives / stores.

### 5.4 Stratégie (résumé)
- Criticité : Auth, Quiz, Data = élevée ; Leaderboard = moyenne ; NFR Perf/Sécu = élevée.
- Effort : unitaires (3 QA-jours), intégration (4), E2E (5), NFR (2).
- Niveaux : unitaires → intégration → système/E2E → acceptation.
- Techniques : basées exigences, partitions, exploratoires, analyse de risque.
- Priorisation exécution : Auth → Quiz → Scores/Leaderboard → NFR → scénarios restants.
- Automatisation : Cypress (E2E), Jest/Jasmine (Angular services), SuperTest (API).
- Suivi : Kanban QA, métriques (% exécution, taux réussite, densité défauts), rapport quotidien.
- Config : env dev/test, `.env` sécurisé, scripts seed (`node addQuestions.js`), snapshots Mongo.
- Gestion défauts : GitHub Issues (workflow Open → Closed, priorisation criticité).  
- Outils : Sheets structurées, Cypress, Postman/Newman, Lighthouse/k6, OWASP ZAP.
- Qualité : revue croisée, Definition of Done QA, rétrospectives qualité.
